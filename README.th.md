[English](README.md) · **ไทย**

สรุปสำหรับ **Microsoft Certified: Security, Compliance, and Identity Fundamentals (SC-900)** เขียนหลังสอบผ่านเดือนกันยายน 2569

โดย [Jarudech Thongkum](https://www.linkedin.com/in/jarudech-thongkum/)

นี่คือสรุปที่ผมเขียนขึ้นเอง ไม่ใช่คลังข้อสอบ และไม่มีเนื้อหาข้อสอบอยู่ในนี้ ดูหัวข้อ [สิ่งที่ไม่มีในนี้](#สิ่งที่ไม่มีในนี้)

เป้าหมายคือให้ *อธิบายออกมาเป็นคำพูดได้* ไม่ใช่แค่จำได้ตอนเห็นตัวเลือก

## สี่บริการหลัก สรุปในภาพเดียว

เนื้อหา SC-900 ส่วนใหญ่คือการรู้ว่าผลิตภัณฑ์ไหนรับผิดชอบปัญหาอะไร อุปมาที่ทำให้ผมจำได้จริงคืออาคารสำนักงานหนึ่งหลัง

| บริการ | เปรียบเป็น | รับผิดชอบ |
|---|---|---|
| **Entra** | ประตูและระบบคีย์การ์ด | ใครเข้าได้ และเข้าถึงอะไรได้ |
| **Purview** | ป้ายกำกับบนเอกสาร และกฎว่าเอกสารออกนอกตึกได้ไหม | ตัวข้อมูลเอง |
| **Defender** | ยามและเซ็นเซอร์ประจำแต่ละห้อง | ตรวจจับและหยุดการโจมตีตรงจุดที่เกิด |
| **Sentinel** | ห้องควบคุมที่รวมจอทุกตัวไว้ผนังเดียว | รวมและเชื่อมโยงสัญญาณจากทุกแหล่ง รวมถึงของที่ไม่ใช่ Microsoft |

## Microsoft Entra

ระบบจัดการตัวตนและสิทธิ์การเข้าถึง ชื่อเดิมคือ Azure Active Directory หน้าที่ของมันคือตอบว่า *คุณเป็นใคร และเข้าถึงอะไรได้บ้าง*

- **Entra ID** คือไดเรกทอรีที่เก็บผู้ใช้ กลุ่ม อุปกรณ์ และแอปพลิเคชัน
- **Authentication** ได้แก่ MFA, passwordless, กุญแจ FIDO2, Windows Hello
- **Conditional Access** คือตัวที่ทำงานหนักที่สุด เป็นนโยบายรูปแบบ *ถ้าเงื่อนไขเป็นแบบนี้ ให้บังคับสิ่งนี้ หรือบล็อกไปเลย* เช่น ล็อกอินจากประเทศที่ไม่คุ้นเคยต้องยืนยัน MFA เพิ่ม หรือเครื่องที่องค์กรไม่ได้จัดการห้ามดาวน์โหลดไฟล์
- **Privileged Identity Management (PIM)** ให้สิทธิ์แอดมินแบบ just-in-time และจำกัดเวลา แทนที่จะค้างอยู่บนบัญชีตลอด
- **Identity governance** ครอบคลุม access review, กระบวนการเข้าย้ายออก และ entitlement management
- **Entra ID Protection** ให้คะแนนความเสี่ยงของการล็อกอินและผู้ใช้ เช่น impossible travel หรือรหัสผ่านที่หลุดออกไปแล้ว

เหตุผลที่หมวดนี้มีน้ำหนักมากในข้อสอบ คือบนคลาวด์ไม่มีขอบเขตเครือข่ายให้ตั้งป้อมป้องกันอีกต่อไป ตัวตนจึงกลายเป็น control plane แทน

## Microsoft Purview

การกำกับดูแลข้อมูลและ compliance ถ้า Entra ปกป้องตัวคน Purview ปกป้องตัวข้อมูลไม่ว่าข้อมูลนั้นจะเดินทางไปที่ไหน

- **Sensitivity labels** จำแนกและติดป้ายให้เนื้อหาว่าเป็น Public, Internal หรือ Confidential โดยมีการเข้ารหัสและลายน้ำผูกไปกับป้าย
- **Data Loss Prevention (DLP)** บังคับว่าข้อมูลที่ติดป้ายแล้วทำอะไรได้บ้าง เช่น ห้ามไฟล์ Confidential ส่งออกทางอีเมลหรือก๊อปลง USB
- **Insider Risk Management** จับสัญญาณความเสี่ยงที่มาจากคนภายในองค์กร
- **eDiscovery และ Audit** ค้นหาและรักษาข้อมูลไว้เมื่อมีคดีความหรือการสอบสวน
- **Data Lifecycle Management** กำหนดว่าข้อมูลต้องเก็บนานเท่าไหร่และลบเมื่อไหร่
- **Compliance Manager** ให้คะแนนและติดตามสถานะเทียบกับกรอบกฎหมายต่าง ๆ

แนวคิดที่ควรจำคือ การปกป้องเดินทางไปกับตัวไฟล์ ไม่ได้ผูกอยู่กับโฟลเดอร์ที่ไฟล์บังเอิญวางอยู่

### สี่ตัวที่ผมสับสนซ้ำ ๆ

หมวดนี้เป็นหมวดที่ผมอ่อนที่สุด สาเหตุคือเหมารวมสี่อย่างนี้เป็นของชิ้นเดียว

| ตัว | ทำอะไรจริง ๆ |
|---|---|
| Sensitive information type | ตรวจจับ pattern เช่นเลขบัตรเครดิต |
| Sensitivity label | เข้ารหัสและจำกัดสิทธิ์ |
| Retention label | กำหนดอายุของข้อมูล |
| Content explorer | ดูว่าไฟล์ที่ติด label *อยู่ที่ไหน* |
| Activity explorer | ดูว่า *ใครทำอะไร* กับไฟล์นั้น |

## Microsoft Defender

การป้องกันภัยคุกคาม Defender เป็นตระกูลผลิตภัณฑ์ ไม่ใช่ตัวเดียว แต่ละตัวเฝ้าคนละพื้นผิว

| ผลิตภัณฑ์ | เฝ้าอะไร |
|---|---|
| Defender for Endpoint | เครื่องลูกข่ายและเซิร์ฟเวอร์ ทำ EDR ตรวจจับพฤติกรรมและตอบสนอง |
| Defender for Office 365 | อีเมลและการทำงานร่วมกัน ทั้งฟิชชิง ลิงก์และไฟล์แนบอันตราย |
| Defender for Identity | การโจมตีที่เล่นงาน Active Directory ภายในองค์กร |
| Defender for Cloud Apps | แอป SaaS ที่พนักงานใช้งานอยู่ (CASB) |
| Defender for Cloud | สถานะความปลอดภัยและ workload บน Azure, AWS และ GCP |
| Defender XDR | ชั้นรวมที่เอาการแจ้งเตือนจากทุกตัวข้างบนมาเชื่อมกัน |

หัวใจอยู่ที่ XDR อีเมลฟิชชิงหนึ่งฉบับ การล็อกอินที่น่าสงสัย โปรเซสแปลก ๆ บนโน้ตบุ๊ก token ที่ถูกนำกลับมาใช้ซ้ำ และการอ่าน storage bucket ไม่ใช่ห้าปัญหา แต่คือการโจมตีครั้งเดียว XDR เย็บทั้งหมดเข้าเป็นเหตุการณ์เดียวที่มีไทม์ไลน์เดียว แทนที่จะเป็นห้าตั๋วในห้าหน้าจอ

## Microsoft Sentinel

SIEM ที่เกิดมาบนคลาวด์ บวกความสามารถ SOAR ถ้า Defender ลงลึกในพื้นที่ของ Microsoft Sentinel จะกวาดกว้าง

- **Data connectors** ดูดข้อมูลจากทุกที่ ทั้ง firewall อุปกรณ์เครือข่าย AWS CloudTrail และเครื่องมือของเจ้าอื่น
- **Analytics rules** คือตรรกะการตรวจจับที่เขียนด้วย KQL เพื่อเปลี่ยนบรรทัดล็อกดิบ ๆ ให้กลายเป็น incident
- **Workbooks** คือแดชบอร์ดและมุมมองสำหรับสืบสวน
- **Playbooks** คือการตอบสนองอัตโนมัติที่สร้างบน Logic Apps เช่น ปิดบัญชีหรือแยกเครื่องออกจากเครือข่าย
- **UEBA** สร้างเส้นฐานพฤติกรรมปกติแล้วจับสิ่งที่เบี่ยงเบนออกไป
- **Threat intelligence** เสริมการตรวจจับด้วยข้อมูลตัวบ่งชี้ที่รู้ว่าเป็นอันตราย

## สองจุดที่คนสับสนบ่อยที่สุด

### Defender ต่างจาก Sentinel อย่างไร

ข้อนี้คือคำถามที่ผมคิดว่าจะโดนถามเป็นอันดับแรก

Defender ตรวจจับและป้องกันภายในขอบเขตของตัวเอง ส่วน Sentinel รวบรวมและเชื่อมโยงข้ามทุกอย่าง รวมถึงสิ่งที่ Defender มองไม่เห็น เช่น firewall ยี่ห้ออื่น บัญชี AWS หรือแอปที่เขียนเองแล้วปล่อยล็อกออกมา Defender ป้อนข้อมูลให้ Sentinel อีกทอด ทั้งสองไม่ได้แข่งกัน

พูดสั้น ๆ คือ **Defender เห็นลึกในบ้านตัวเอง Sentinel เห็นกว้างทั้งเมือง**

### Entra ต่างจาก Defender for Identity อย่างไร

Entra คือคนที่ *จัดการ* ตัวตน ส่วน Defender for Identity คือคนที่ *เฝ้าดูว่ามีใครโจมตี* ตัวตนอยู่หรือเปล่า

Entra เป็นทั้งฐานข้อมูลหลักและเครื่องบังคับใช้นโยบาย ทั้งสร้างบัญชี ให้บทบาท บังคับ MFA และทบทวนสิทธิ์ ส่วน Defender for Identity คือเซ็นเซอร์ที่คอยดูว่ามีใครใช้ชั้นตัวตนนั้นไปในทางที่ผิด เช่น lateral movement, การโจมตี Kerberos หรือการสอดส่อง domain controller

## Zero Trust

มีสามหลักการ และข้อที่สามคือข้อที่เปลี่ยนวิธีคิดของผม

1. **Verify explicitly** ยืนยันตัวตนและให้สิทธิ์โดยดูจากทุกสัญญาณที่มี ทั้งตัวตน สุขภาพอุปกรณ์ ตำแหน่ง workload และความอ่อนไหวของข้อมูล การอยู่ในเครือข่ายบริษัทไม่ใช่หลักฐานอะไรทั้งนั้น
2. **Least privilege access** ให้สิทธิ์เท่าที่จำเป็น เท่าที่ต้องใช้ และเท่าช่วงเวลาที่ต้องใช้ พร้อมนโยบายที่ปรับตามความเสี่ยง
3. **Assume breach** ออกแบบโดยสมมติว่าผู้โจมตีอยู่ข้างในแล้ว แบ่งโซน เข้ารหัสตลอดเส้นทาง ตรวจสอบต่อเนื่อง และจำกัดขอบเขตความเสียหายให้เล็กที่สุด

### ทำไม assume breach ไม่ใช่การยอมแพ้

มันเปลี่ยนคำถามที่ตอบไม่ได้ คือ *จะทำยังไงให้ไม่โดนเจาะเลย* ไปเป็นคำถามที่วัดได้ คือ **เมื่อ identity หนึ่งตัวถูกยึด มันเอื้อมถึงอะไรได้บ้าง**

คำถามหลังนี้วัดเป็นตัวเลขได้ ผมเลยลองวัดดู

> **โปรเจกต์ที่เกี่ยวข้อง:** [iam-blast-radius-lab](https://github.com/olafier/iam-blast-radius-lab) การทดลองแบบมีการควบคุม ครอบคลุม 100 actions บน 12 AWS services เปรียบเทียบ IAM policy สามระดับ นโยบายแบบแคบได้ blast radius แบบถ่วงน้ำหนัก **3.9%** ส่วนนโยบายแบบ PowerUser ได้ **77.6%** identity ตัวเดียวกัน การถูกยึดแบบเดียวกัน แต่ผลต่างกันเกือบยี่สิบเท่า จากวิธีเขียน policy เท่านั้น

หลักการข้อ 2 กับข้อ 3 คือประโยคเดียวกันที่อ่านจากคนละทิศ

### Shared responsibility

ความรับผิดชอบขยับไปตามรูปแบบบริการ

| | On-premises | IaaS | PaaS | SaaS |
|---|---|---|---|---|
| กายภาพ โฮสต์ เครือข่าย | ลูกค้า | ผู้ให้บริการ | ผู้ให้บริการ | ผู้ให้บริการ |
| ระบบปฏิบัติการและแพตช์ | ลูกค้า | **ลูกค้า** | ผู้ให้บริการ | ผู้ให้บริการ |
| แอปพลิเคชัน | ลูกค้า | ลูกค้า | **ร่วมกัน** | ผู้ให้บริการ |
| **ตัวตนและสิทธิ์** | ลูกค้า | **ลูกค้า** | **ลูกค้า** | **ลูกค้า** |
| **ข้อมูล** | ลูกค้า | **ลูกค้า** | **ลูกค้า** | **ลูกค้า** |

สองแถวล่างสุดไม่เคยขยับ ตัวตนและข้อมูลเป็นความรับผิดชอบของลูกค้าเสมอในทุกรูปแบบบริการ และเหตุการณ์ความปลอดภัยบนคลาวด์ส่วนใหญ่ก็เกิดในสองแถวนั้นพอดี

## ผมเตรียมตัวอย่างไร

สองสัปดาห์ ควบคู่ไปกับการเรียนในมหาวิทยาลัย

ข้อสอบซ้อมรอบแรกผมได้ 58% และหมวดที่แย่ที่สุดคือ compliance ได้ 38% สัญชาตญาณแรกคืออยากไปไล่ทำข้อสอบเพิ่ม แต่สิ่งที่ช่วยจริงคือหยุดแล้วหาให้เจอว่าตัวเองพลาด *หมวดไหน* ซ้ำ ๆ แล้วกลับไปอ่านเฉพาะหมวดนั้น พอแยกสี่ตัวของ Purview ข้างบนออกจากกันได้ คะแนน compliance ในชุดถัดมาขึ้นไปถึง 100%

**แต่ข้อสอบจริงบอกอีกอย่าง** compliance ยังเป็นหมวดที่ผมทำได้แย่ที่สุดในใบคะแนน

ผมคิดว่าเป็นเพราะรูปแบบคำถาม ข้อสอบซ้อมที่ผมทำเป็นโจทย์สถานการณ์ยาว ๆ เกือบหมด ซึ่งบริบทในโจทย์ช่วยตัดตัวเลือกไปครึ่งหนึ่งแล้ว แต่ข้อสอบจริงถามความหมายตรง ๆ ไม่มีอะไรให้เกาะ แปลว่าสิ่งที่ผมซ่อมได้คือความสามารถในการตอบ *โจทย์สถานการณ์เรื่อง compliance* ไม่ใช่ความรู้เรื่อง Purview ตัวเลข 100% ที่ทำให้ผมสบายใจ มันวัดผิดเรื่องมาตั้งแต่แรก

นั่นคือส่วนที่อยากส่งต่อมากที่สุด การเลือกเครื่องมือวัดผิดตัวจะทำให้เราเชื่อว่าตัวเองเก่งในสิ่งที่ยังไม่เก่ง

สิ่งที่อยากบอกคนที่กำลังจะเริ่ม SC-900

- อย่าท่องชื่อผลิตภัณฑ์ ให้เรียนว่าผลิตภัณฑ์ไหนรับผิดชอบปัญหาอะไร แล้วทุกคำถามจะง่ายขึ้น
- ทำข้อสอบวัดระดับตั้งแต่ต้น อย่าเก็บไว้ท้าย คะแนนแย่ตอนเริ่มคือข้อมูล คะแนนแย่ตอนคืนก่อนสอบคือความตื่นตระหนก
- พูดคำตอบออกมาดัง ๆ ถ้าอธิบายความต่างระหว่าง Defender กับ Sentinel โดยไม่เปิดโน้ตไม่ได้ แปลว่ายังไม่รู้จริง
- ซ้อมหลายรูปแบบคำถาม ถ้าซ้อมแต่โจทย์สถานการณ์อย่างเดียว จะประเมินตัวเองสูงเกินจริง

## สิ่งที่ไม่มีในนี้

**ไม่มีข้อสอบ ไม่มีเนื้อหาที่จำมาจากห้องสอบ ไม่มีสื่อการเรียนของคนอื่นที่เอามาเผยแพร่ต่อ**

[นโยบายความปลอดภัยของข้อสอบ Microsoft](https://learn.microsoft.com/en-us/credentials/support/exam-and-assessment-lab-security-policies) ระบุว่าเนื้อหาข้อสอบเป็นทรัพย์สินทางปัญญาที่เป็นความลับ การเผยแพร่รวมถึงการจำมาเขียนใหม่ มีโทษถึงขั้นเพิกถอนใบรับรองที่มีอยู่และห้ามสอบตลอดชีวิต ส่วนคอร์สที่ต้องเสียเงินของเจ้าอื่นก็มีลิขสิทธิ์และเงื่อนไขการใช้งานคุ้มครองอยู่แยกต่างหาก

ทุกอย่างในที่นี้เขียนด้วยคำพูดของผมเอง จากเอกสารสาธารณะและจากการอ่านของตัวเอง
